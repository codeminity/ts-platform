# Contributing to `@codeminity/ui-kit-core`

Follow the shape `button` already establishes:

1. Create `src/components/<name>/<name>.ts`. The custom element tag is `cdmt-<name>` (kebab-case, always prefixed with `cdmt-` to avoid colliding with native elements or another library's custom elements).
2. Any color/font/radius/transition value should be themeable: use `themeVar('tokenKey')` (`src/theme/css-var.ts`) directly at each CSS property that needs it — never re-declare `--cdmt-*` on `:host` with a hardcoded default (breaks inheritance from `applyTheme`) and never combine a `transition` on the same CSS property that also derives its value from a token (freezes the property in Chromium). See [DECISIONS.md#adr-006](./DECISIONS.md#adr-006-per-use-site-var-fallbacks-not-a-blanket-host-token-block) for why, and `button.ts` for the working shape.
3. Use Lit's plain `static properties` field — **not decorators** — matching `button.ts`. This is deliberate, not a stopgap: standard TC39 decorators aren't lowered by Oxc yet (Vite 8's default transformer; tracked at [oxc#9170](https://github.com/oxc-project/oxc/issues/9170), no timeline), and legacy `experimentalDecorators` is the TS-only mechanism TypeScript itself is moving away from. `static properties` depends on neither. Declare each reactive field with `declare` (no initializer — a real field would shadow Lit's own accessor) and set actual defaults in the constructor. Register the element with a plain `customElements.define('cdmt-<name>', Cdmt<Name>)` call after the class. No Vue/React/Angular import, ever (see [ARCHITECTURE.md](./ARCHITECTURE.md)).
4. Add the `declare global { interface HTMLElementTagNameMap { ... } }` block so `document.querySelector('cdmt-<name>')` is typed for consumers.
5. Write `src/components/<name>/<name>.test.ts` alongside it — render via `document.body.innerHTML`, await `el.updateComplete`, assert against the real rendered shadow DOM (see `button.test.ts`). Start the file with a `// @vitest-environment happy-dom` comment — this repo's global Vitest environment is `node` (everything else here is DOM-free), so every `ui-kit` test file opts into a DOM per file. Same 100%-coverage bar as the rest of this monorepo. **`happy-dom` cannot verify theming** (it doesn't resolve CSS custom-property inheritance/`var()` fallbacks like a real browser) — if the component introduces a new themeable property, add or extend a spec under `e2e/` instead (see `e2e/apply-theme.spec.ts`).
6. Export the component (and any public types) from `src/index.ts`.
7. Run `pnpm --filter @codeminity/ui-kit-core build && pnpm --filter @codeminity/ui-kit-core test` before opening a PR — also see the root [CONTRIBUTING.md](../../../CONTRIBUTING.md) for the full local check and changeset requirements.

Framework-specific bindings (a Vue/React/Angular wrapper around a `core` component) live in their own sibling package once one is actually needed by a real consumer — not added speculatively alongside the component itself.
